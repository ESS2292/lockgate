bun install --frozen-lockfile in CI: “lockfile had changes, but lockfile is frozen”

Your CI job runs bun install --frozen-lockfile or bun ci and fails with error: lockfile had changes, but lockfile is frozen. That is Bun doing its job: package.json changed and bun.lock was not regenerated and committed. The harder problem is the opposite case, where the install is not frozen and nothing fails.

Everything below was run on 20 November 2026 with Bun 1.4.4 and 1.4.5 (1.4.5 is the current latest on npm), plus Bun 1.2.23 and 1.1.38 for comparison, on Linux. The test project had a committed bun.lock for is-number@^7.0.0, then gained "left-pad": "^1.3.0" in package.json without a lockfile update.

The exact error

With the stale lockfile, bun install --frozen-lockfile on Bun 1.4.5 exited 1 and printed:

bun install v1.4.5 (a7733435c)
warn: deprecated left-pad@1.3.0: use String.prototype.padStart()
error: lockfile had changes, but lockfile is frozen
note: dependencies in package.json changed since bun.lock was saved: left-pad was added
note: try re-running without --frozen-lockfile and commit the updated lockfile

bun ci printed the same error and also exited 1. Bun 1.4.4 printed the same error and notes. In every failing run, bun.lock on disk was left unchanged.

The fix is on the developer machine, not in CI: run bun install, commit bun.lock, and push. The bun install docs say the same: “Run bun install and commit the updated bun.lock to fix it.”

Bun does not freeze on CI by default

pnpm and Yarn Berry switch to a frozen install when they detect CI. Bun does not. The bun install docs state: “Bun does not enable --frozen-lockfile automatically in CI; pass the flag or use bun ci.”

We confirmed it. With the same stale lockfile, CI=true bun install on Bun 1.4.4 printed Saved lockfile, installed left-pad@1.3.0, rewrote bun.lock, and exited 0. The CI job goes green while installing a tree that nobody committed. So the first fix is the command itself:

steps:
  - uses: actions/checkout@v6
  - uses: oven-sh/setup-bun@v2
  - run: bun ci          # same as bun install --frozen-lockfile

The docs describe bun ci as “equivalent to bun install --frozen-lockfile” and add: “To use bun ci or bun install --frozen-lockfile, you must commit bun.lock to version control.” They also say --production implies --frozen-lockfile; on the stale project, bun install --production failed with the same error.

--frozen-lockfile with no lockfile passes

If bun.lock is not in the checkout (gitignored, never committed, or excluded from a Docker build context), the frozen flag does not catch it. In a directory with only package.json, Bun 1.4.4 ran bun install --frozen-lockfile, resolved is-number@7.0.0 from the registry, wrote no lockfile, and exited 0. bun ci did the same. The docs confirm it: “If there is no lockfile at all, --frozen-lockfile installs from package.json without writing one.”

So a frozen flag is only as good as the lockfile that reaches the install. Check that bun.lock is committed and copied, not only that the flag is present.

Pin the Bun version

The lockfile format changes between Bun versions, and an older Bun in CI can fail on a lockfile that is perfectly in sync. In our runs, Bun 1.4.4 wrote "lockfileVersion": 2. Bun 1.2.23 could not read it, even with package.json unchanged:

bun install v1.2.23 (cf136713)
2 |   "lockfileVersion": 2,
                         ^
error: Unknown lockfile version
    at bun.lock:2:22
UnknownLockfileVersion: failed to parse lockfile: 'bun.lock'

warn: Ignoring lockfile
error: lockfile had changes, but lockfile is frozen

That run exited 1. The other direction worked: Bun 1.4.5 accepted a "lockfileVersion": 1 lockfile written by 1.2.23 under --frozen-lockfile, exited 0, and left it unchanged.

Older Bun can be worse than a failure. Bun 1.1.38 did not use the committed bun.lock: on the stale project, bun install --frozen-lockfile installed left-pad@1.3.0, wrote no lockfile, and exited 0.

oven-sh/setup-bun (latest release v2.2.0) reads the version from package.json when you do not pass one. Its README says it checks the packageManager field first, then engines.bun, then falls back to latest. It also accepts bun-version and bun-version-file (for example .bun-version or .tool-versions). Pin the version so local and CI write and read the same lockfile format:

{
  "packageManager": "bun@1.4.5"
}

bun.lockb vs bun.lock

Per the Bun lockfile docs, “Bun v1.2 changed the default lockfile format to the text-based bun.lock.” Older projects may still commit the binary bun.lockb. Bun 1.4.5 still honors it: on a bun.lockb written by Bun 1.1.38, --frozen-lockfile installed and exited 0 when it was in sync, and failed with the same “lockfile had changes” error (naming bun.lockb) after left-pad was added to package.json.

The docs give the migration command: bun install --save-text-lockfile --frozen-lockfile --lockfile-only, then delete bun.lockb. On Bun 1.4.5 that wrote bun.lock, exited 0, and bun.lockb was already gone afterwards. bun ci on the result exited 0. A text lockfile is also reviewable in a pull request, which a binary one is not.

Dockerfile: copy bun.lock before the install

The lockfile has to be in the build context when the install runs, and the install should be frozen. Docker builds are not CI to Bun either way, since Bun never freezes by default:

FROM oven/bun:1
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .

If COPY only copies package.json, or .dockerignore lists bun.lock, the install inside the image runs without a lockfile, which is the case shown above where --frozen-lockfile resolved from the registry and exited 0. The image is then built from whatever the registry served that day.

How LockGate catches this

These are the Bun-related checks in the current LockGate code, confirmed against its source and its 85-test suite on 20 November 2026. We ran them on a sample repo with the stale bun.lock, a workflow step run: bun install, and a Dockerfile that copied only package.json before RUN bun install. The full CLI exited 1 with:

LockGate checked 1 package.json file and 1 lockfile.

Errors (4):
  [lockfile-out-of-sync] package.json declares left-pad@^1.3.0, but bun.lock has no entry for it.
  [unfrozen-ci] .github/workflows/ci.yml:8 runs `bun install`, which can update the lockfile or resolve a different tree. Use bun ci or bun install --frozen-lockfile.
  [unfrozen-docker] Dockerfile runs `bun install`. Use bun install with a frozen-lockfile flag so the image installs the committed tree.
  [docker-missing-lockfile] Dockerfile installs with bun but does not COPY a bun lockfile before the install.

After regenerating bun.lock, switching the workflow to bun ci, and using the Dockerfile above, it printed OK — lockfiles and install commands look frozen. and exited 0. The checks:

  • Unfrozen CI install (error). A GitHub Actions run: step with bun install or bun i and no --frozen-lockfile. bun ci counts as frozen; bun add is skipped. Unlike pnpm, this is an error, not a warning, because Bun has no CI default.
  • Missing lockfile (error). A package.json with dependencies and no lockfile in its directory or above. This is the case --frozen-lockfile lets through.
  • Manifest vs bun.lock (error, full CLI only). Each direct dependency must have a matching entry in the text bun.lock, including workspaces, without running an install.
  • Dockerfile checks (full CLI only). A RUN bun install without a frozen flag (error), a Bun install before any COPY of bun.lock or bun.lockb (error), and a lockfile listed in .dockerignore (error).
  • packageManager mismatch (error). "packageManager": "bun@1.4.5" next to a package-lock.json reported package.json sets packageManager to bun, but the lockfile in scope is for npm.
  • Mixed lockfiles (error). bun.lock next to package-lock.json, yarn.lock, or pnpm-lock.yaml in the same directory.

Limits, stated plainly: LockGate does not run Bun and does not check which Bun version is pinned, so it will not catch the lockfile-version failure above. It does not parse the binary bun.lockb; a repo with only bun.lockb got a warning (bun.lockb is a binary bun lockfile. LockGate can check manifest sync on text bun.lock, not bun.lockb.) and exited 0 even though that lockfile was stale. It treats any flag beginning with --frozen-lockfile as frozen, so --frozen-lockfile=false is not flagged, and it flags bun install --production as unfrozen even though Bun treats it as frozen. Workflow and Dockerfile parsing is best-effort.
