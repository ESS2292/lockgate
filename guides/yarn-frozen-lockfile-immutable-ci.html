yarn install --frozen-lockfile vs yarn --immutable in CI

Yarn has two frozen-install flags because it has two lines of releases. Use the wrong one and CI either fails for the wrong reason or, on Yarn 1, quietly rewrites yarn.lock and passes.

Yarn 1 (“classic”) and Yarn 2+ (“Berry”, currently 4.x) both read a file called yarn.lock, but they spell “do not touch the lockfile” differently. Everything below was run on 15 November 2026 with Yarn 1.22.22 and Yarn 4.9.2 (through Corepack) against a package.json that had gained a dependency the lockfile did not record.

Yarn 1 (classic): --frozen-lockfile

The Yarn classic install docs describe --frozen-lockfile as “Don’t generate a yarn.lock lockfile and fail if an update is needed,” and recommend it for continuous integration. Running bare yarn is the same as yarn install and passes flags through, so yarn --frozen-lockfile works too.

yarn install --frozen-lockfile

With a stale lockfile, Yarn 1.22.22 exits 1 with:

error Your lockfile needs to be updated, but yarn was run with `--frozen-lockfile`.

Two traps on Yarn 1:

  • No CI default. With CI=true set and no flag, Yarn 1.22.22 resolved the new dependency, printed success Saved lockfile., and exited 0. CI goes green on a tree nobody committed.
  • --immutable is silently ignored. yarn install --immutable on Yarn 1.22.22 also rewrote yarn.lock and exited 0. A workflow copied from a Berry project gives you no protection on a classic project.

--pure-lockfile is a different flag: it does not write yarn.lock, but it does not fail when an update is needed either. For a CI gate you want --frozen-lockfile.

Yarn Berry (2+): --immutable

The Yarn Berry install docs say that with --immutable “Yarn will abort with an error exit code if the lockfile was to be modified,” and that the option defaults to true on CI. --frozen-lockfile is kept as a backward-compatible alias that “will be removed in a later release.”

yarn install --immutable

With a stale lockfile, Yarn 4.9.2 exits 1 with:

YN0028: The lockfile would have been modified by this install, which is explicitly forbidden.

Observed behavior on Yarn 4.9.2:

  • yarn install --frozen-lockfile printed YN0050: The --frozen-lockfile option is deprecated; use --immutable and/or --immutable-cache instead and then failed with the same YN0028 error. It works today, but it is on its way out.
  • CI=true yarn install (no flag) also failed with YN0028, matching the documented CI default.
  • Plain yarn install without CI set rewrote the lockfile and exited 0.

Because the CI default depends on Yarn detecting CI, write the flag anyway. A docker build step, a self-hosted runner script, or a local “reproduce CI” command may not look like CI to Yarn. For Zero-Installs projects the docs also show --immutable --immutable-cache, plus --check-cache if you accept pull requests from forks.

Pin the Yarn version: packageManager and Corepack

The flag you need depends on which Yarn actually runs, so pin it. The packageManager field in package.json tells Corepack which manager and version to use, for example:

{
  "packageManager": "yarn@4.9.2"
}

With Corepack enabled (corepack enable), yarn then runs that exact version. Corepack has shipped with Node.js since 14.19.0 and 16.9.0, through the 24.x line, as an experimental tool you opt into. Per the Node.js distribution policy, it is no longer distributed as of Node.js 25.0.0; on Node 25+ install it with npm install -g corepack first.

Dockerfile: copy yarn.lock before the install

A frozen flag only helps if the lockfile is in the build context at install time. This order fails the build on a stale lock instead of resolving a new tree:

# Yarn 1
COPY package.json yarn.lock ./
RUN yarn install --frozen-lockfile
COPY . .
# Yarn Berry with Corepack (Node 24 or earlier base image)
RUN corepack enable
COPY package.json yarn.lock .yarnrc.yml ./
RUN yarn install --immutable
COPY . .

Drop .yarnrc.yml from the COPY if the project has none, because COPY fails on a missing source. If your .yarnrc.yml sets yarnPath, also copy the .yarn/releases directory it points to before the install. If yarn.lock is not copied (for example only COPY package.json ./), Yarn has nothing to freeze against and resolves from scratch; check .dockerignore does not list yarn.lock either. Do not rely on Berry’s CI default inside an image: name --immutable explicitly.

How LockGate catches this

These are the Yarn-related checks in the current LockGate code, confirmed against its source and test suite on 15 November 2026:

  • Unfrozen CI install (error). A GitHub Actions run: step with yarn or yarn install and neither --frozen-lockfile nor --immutable. yarn add, yarn run, and similar are not install steps and are skipped.
  • Implicit CI freeze (warning). If the committed yarn.lock is a Berry lockfile (it has a __metadata: block), a bare yarn install in CI is a warning rather than an error, because Berry already freezes on CI. The warning asks you to make --immutable explicit.
  • packageManager mismatch (error). package.json names one manager in packageManager (say pnpm@9.12.0) but the lockfile in scope is yarn.lock.
  • Mixed lockfiles (error). yarn.lock next to package-lock.json, pnpm-lock.yaml, or a bun lockfile in the same directory.
  • Manifest vs yarn.lock (error, full CLI only). A direct dependency in package.json that is missing from yarn.lock, whose locked version does not satisfy the range, or (Berry workspaces) whose specifier no longer matches. Covers Yarn classic and Berry lockfiles, including workspaces, without running an install.
  • Dockerfile checks (full CLI only). A RUN yarn install without a frozen flag (a warning for Berry lockfiles, an error otherwise), a Yarn install before any COPY of yarn.lock, and a yarn.lock listed in .dockerignore.

Limits, stated plainly: LockGate accepts either flag as frozen whatever Yarn version runs. It does not know that Yarn 1 ignores --immutable, and its packageManager check compares the manager name only, so "yarn@4.9.2" next to a classic yarn.lock is not flagged. It does not check .yarnrc.yml, yarnPath, or .yarn/releases in Docker builds.
