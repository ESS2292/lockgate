Don't commit pnpm-lock.yaml and package-lock.json together

Two lockfiles in one directory are not a backup. They are two sources of truth, and CI will pick one of them.

npm, Yarn, pnpm, and bun each write a different lockfile. If more than one is committed in the same directory, a teammate who runs npm install and a CI job that runs pnpm install --frozen-lockfile can install different trees from the same commit. The leftover lockfile is often stale.

That failure mode is documented. dclarktech302/nightdeck #19 (15 October 2026) has both pnpm-lock.yaml and package-lock.json at the root. The package-lock.json is missing next-themes (declared in package.json as ^0.4.6), so npm ci fails, while pnpm install --frozen-lockfile succeeds. The project was using pnpm; the npm lockfile was the one that had drifted.

The same question comes up with Yarn. The Stack Overflow thread Should I commit yarn.lock and package-lock.json files? has a score of 186 and 126,119 views (Stack Exchange API, 10 November 2026). The usual answer is: pick one package manager, commit that manager's lockfile, and do not commit the other.

Pick one manager, and fail if a second lockfile appears

A practical pattern is: choose npm, Yarn, pnpm, or bun for the repository; commit only that lockfile; put the Corepack packageManager field in package.json if you want the version pinned too; and add a CI check that fails when a second lockfile shows up.

Tools such as pnpm's only-allow can block the wrong package manager at install time via a preinstall script. They do not inspect the tree for a leftover lockfile, and they do not catch an unfrozen npm install in a workflow. A scan that looks at the committed files and the CI run: steps covers that gap.
