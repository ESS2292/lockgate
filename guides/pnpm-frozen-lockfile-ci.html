pnpm install --frozen-lockfile in CI: ERR_PNPM_OUTDATED_LOCKFILE explained

Your branch passes locally and pnpm install fails in CI with ERR_PNPM_OUTDATED_LOCKFILE. That is pnpm doing its job: package.json changed and pnpm-lock.yaml was not regenerated and committed.

Everything below was run on 15 November 2026 with pnpm 12.21.0 (the current latest on npm), plus pnpm 10.34.9 and 9.15.9 for comparison, on Node.js 24.22.1. The test project had a committed pnpm-lock.yaml for is-number@^7.0.0, then gained "left-pad": "^1.3.0" in package.json without a lockfile update.

The CI default: frozen-lockfile is on

The pnpm install docs list the --frozen-lockfile default as false for non-CI and “true, if a lockfile is present” for CI. With it on, pnpm “doesn’t generate a lockfile and fails to install if the lockfile is out of sync with the manifest.” pnpm detects CI with the same rules as the ci-info package, and the docs say to set CI=false to turn detection off. GitHub Actions sets CI=true on its runners, so a bare pnpm install there is already frozen.

The exact error

With CI=true and a stale lockfile, pnpm 12.21.0 exited 1 and printed:

Error: ERR_PNPM_OUTDATED_LOCKFILE

  × installing dependencies
  ╰─▶ Cannot install with "frozen-lockfile" because pnpm-lock.yaml is not up
      to date with package.json.
      
        Failure reason:
        specifiers in the lockfile don't match specifiers in package.json:
      * in importers["."]:
      * 1 dependency was added: left-pad@^1.3.0
  help: Regenerate the lockfile with `pnpm install --lockfile-only` so that
        pnpm-lock.yaml reflects the current package.json, then re-run `pnpm
        install --frozen-lockfile`.

pnpm 10.34.9 printed the older single-line form most CI logs still show, and also exited 1:

 ERR_PNPM_OUTDATED_LOCKFILE  Cannot install with "frozen-lockfile" because pnpm-lock.yaml is not up to date with <ROOT>/package.json

Note that in CI environments this setting is true by default. If you still need to run install in such cases, use "pnpm install --no-frozen-lockfile"

  Failure reason:
  specifiers in the lockfile don't match specifiers in package.json:
* 1 dependencies were added: left-pad@^1.3.0

pnpm 9.15.9 printed the same first line and note, with the failure reason written as specifiers in the lockfile ({"is-number":"^7.0.0"}) don't match specs in package.json ({"is-number":"^7.0.0","left-pad":"^1.3.0"}). In every failing run the lockfile on disk was left unchanged.

The fix is on the developer machine, not in CI: run pnpm install (or pnpm install --lockfile-only, which the docs describe as updating only pnpm-lock.yaml and package.json), commit pnpm-lock.yaml, and push.

With and without CI=true

Same stale lockfile, pnpm 12.21.0, each run starting from the committed lockfile:

  • CI=true pnpm install: failed with ERR_PNPM_OUTDATED_LOCKFILE, exit 1.
  • CI=true pnpm install --frozen-lockfile: same failure, exit 1.
  • pnpm install with CI unset: resolved left-pad 1.3.0, rewrote pnpm-lock.yaml, exit 0.
  • pnpm install --frozen-lockfile with CI unset: failed with ERR_PNPM_OUTDATED_LOCKFILE, exit 1.
  • GITHUB_ACTIONS=true pnpm install with CI unset: exit 1, so detection is not only the CI variable.

pnpm 10.34.9 and 9.15.9 behaved the same way: fail with CI=true, rewrite and exit 0 without it. The takeaway is to write --frozen-lockfile explicitly. A docker build, a self-hosted runner script, or a “reproduce CI locally” command may not look like CI to pnpm, and then a bare pnpm install quietly updates the lockfile and passes.

--no-frozen-lockfile

--no-frozen-lockfile is the documented inverse and lets pnpm update the lockfile during the install. CI=true pnpm install --no-frozen-lockfile on pnpm 12.21.0 rewrote pnpm-lock.yaml and exited 0. It makes the red build go away, but CI then installs a tree that nobody reviewed or committed, and the next run may resolve differently. Use it for a deliberate lockfile-update job, not to silence the error.

Pin the pnpm version: packageManager and Corepack

The error text, lockfile format, and defaults change between pnpm majors, so pin the version. The packageManager field in package.json names the manager and exact version:

{
  "packageManager": "pnpm@12.21.0"
}

With Corepack, pnpm then runs that version. Corepack 0.36.0 on Node.js 24.22.1 read this field, downloaded pnpm 12.21.0, and reproduced the same ERR_PNPM_OUTDATED_LOCKFILE failure. Per the Node.js distribution policy, Corepack is no longer distributed as of Node.js 25.0.0; on Node 25+ install it with npm install -g corepack first, or install pnpm another way.

GitHub Actions: pnpm/action-setup

pnpm/action-setup (latest release v6.1.1) installs pnpm on the runner. Its README says the version input can be omitted when package.json declares pnpm in packageManager; otherwise it is required. The README also points pnpm 11+ users to pnpm/setup as an alternative that can install Node.js in the same step.

steps:
  - uses: actions/checkout@v6
  - uses: pnpm/action-setup@v6   # reads packageManager from package.json
  - uses: actions/setup-node@v4
    with:
      node-version: 24
  - run: pnpm install --frozen-lockfile

The explicit flag is redundant on a GitHub-hosted runner today, but it documents intent and keeps the step frozen if the script is reused somewhere that is not detected as CI.

Dockerfile: copy pnpm-lock.yaml (and pnpm-workspace.yaml) before the install

The lockfile has to be in the build context when the install runs:

# Node 24 or earlier base image, packageManager set in package.json
RUN corepack enable
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY . .

In a workspace, copy pnpm-workspace.yaml and every workspace package.json before the install as well. We tested what happens if you forget it: a workspace whose only dependency was in packages/a, built with root package.json, pnpm-lock.yaml, and packages/a/package.json but no pnpm-workspace.yaml. CI=true pnpm install --frozen-lockfile on pnpm 12.21.0 printed Already up to date, exited 0, and installed nothing into packages/a. Adding pnpm-workspace.yaml installed is-number there. No error, just a broken image.

The .dockerignore trap

If .dockerignore lists pnpm-lock.yaml, the COPY above fails on a missing source, and a COPY . . silently leaves the lockfile out. What pnpm does next depends on the flag. With no lockfile present, pnpm 12.21.0 gave:

  • CI=true pnpm install --frozen-lockfile: exit 1 with Error: ERR_PNPM_NO_LOCKFILE and “Headless installation requires a pnpm-lock.yaml file, but none was found.”
  • CI=true pnpm install (no flag): resolved from scratch, wrote a new pnpm-lock.yaml, exit 0. The CI default only applies “if a lockfile is present.”

So the explicit flag is what turns a missing lockfile into a failed build instead of an image built from whatever the registry served that day.

How LockGate catches this

These are the pnpm-related checks in the current LockGate code, confirmed against its source and test suite on 15 November 2026, and run against the stale-lockfile project above:

  • Implicit CI freeze (warning). A GitHub Actions run: step with pnpm install or pnpm i and no --frozen-lockfile is a warning, not an error, because pnpm already freezes on CI. The message asks you to make the flag explicit. pnpm add and other commands are not install steps and are skipped.
  • packageManager mismatch (error). package.json sets packageManager to pnpm@… but the lockfile in scope belongs to another manager, such as package-lock.json.
  • Mixed lockfiles (error). pnpm-lock.yaml next to package-lock.json, yarn.lock, or a bun lockfile in the same directory.
  • Missing lockfile (error). A package.json with dependencies and no lockfile in its directory or above.
  • Manifest vs pnpm-lock.yaml (error, full CLI only). For lockfile v6 and v9, including workspace importers: a direct dependency missing from the importer, an importer specifier that differs from package.json, a locked version outside the range, or a dependency the importer still records after it was removed. On the test project it reported package.json declares left-pad@^1.3.0, but pnpm-lock.yaml has no entry for it. without running an install.
  • Dockerfile checks (full CLI only). A RUN pnpm install without --frozen-lockfile (warning), a pnpm install before any COPY of pnpm-lock.yaml (error), and pnpm-lock.yaml listed in .dockerignore (error).

Limits, stated plainly: LockGate does not run pnpm or check which pnpm version is pinned; its packageManager check compares the manager name only. It treats any flag beginning with --frozen-lockfile as frozen, so --frozen-lockfile=false is not flagged, and pnpm install --no-frozen-lockfile in a workflow only gets the implicit-CI-freeze warning even though it disables the freeze. It does not check that a Dockerfile copies pnpm-workspace.yaml or workspace manifests, it skips commands written as pnpm --filter … install, and lockfile versions other than v6 and v9 get a warning instead of a sync check.
